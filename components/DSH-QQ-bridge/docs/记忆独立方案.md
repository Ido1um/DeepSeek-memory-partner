# 记忆功能独立方案（数据集中 + 程序独立）

> 历史版本（2026-10-26/27 起草）：实现已于 2026-10-29 迁移到独立包 `<DSMP_MEMORY_SRC>`（@local/deepseek-memory），桥接只保留适配层；路径与命令以 `README.md` 与 `HANDOFF-7day-memory.md` 为准。


> 2026-10-27 起草。目标：① 所有记忆文件集中到 `<DSMP_MEMORY_DIR>`；② 记忆功能从 qq-bridge 里抽出来，做成一个可独立安装/升级的程序，放在 `<DSMP_MEMORY_SRC>`。

## 0. 结论先说

- **数据集中：可以做到，且大部分已经在了。** 缺口只有三块：DSH 原生记忆（`~\.dsh\memories`）、桥接状态文件（`state\sessions.json` 等，其实不算记忆）、角色卡（`roles\<PERSONA>.md`，是人设不是记忆）。前两块处理方式见 §2；角色卡建议留在桥接仓库（跟人格走）。
- **打包独立程序：可以。** 推荐先做「**本地库 + 薄适配**」（形态 A），几天内可落地、风险最低；需要给别的程序（CLI/别的 Bot）共用记忆时再演进到「**独立 sidecar 进程**」（形态 B）；DSH Cordis 插件（形态 C）只适合做查看面板，不能替代桥接侧的采集钩子。

## 1. 现状盘点

### 1.1 已经在 shenming 里的

| 文件/目录 | 归属 | 说明 |
| --- | --- | --- |
| `hot\YYYY-MM-DD\private_<OWNER_QQ>.jsonl` | 原文（窗口内） | 每条消息一行 JSON |
| （`archive\YYYY-MM\…`） | 原文（窗口外） | 目前还没有超窗数据，第一次轮转会生成 |
| `digests\*.md` | 交接摘要 | 每次轮转一份 |
| `profile.md`（+`.bak-*`） | 长期事实卡 | 每日 23:00 由模型刷新 |
| `state\memory.json` | 记忆状态 | 会话起点、chars、轮转计数、handover、`recentIds`、`autoHandoverFor` |
| `logs\bridge.log` 等 4 个 | 运行日志 | 由 `config.logDir` 指向这里 |

### 1.2 还在外面的

| 文件/目录 | 归属 | 能否迁到 shenming | 建议 |
| --- | --- | --- | --- |
| `<USER_HOME>\.dsh\memories\` | DSH 原生记忆（`memory` 工具：MEMORY/USER/KEY/daily/SUGGESTIONS） | 不能直接改路径（路径由 DSH_HOME 推导） | junction 或每日镜像，见 §2.1 |
| `<DSMP_BRIDGE_DIR>\state\sessions.json`、`social-v2.json` 等 | 桥接运行状态（映射/缓存） | 物理上能放，但**不能移**：移动后老映射与权限缓存全部失效，需重建会话 | 留在 `state\`，不进 shenming |
| `roles\<PERSONA>.md` | 角色卡/人设 | 能 | 留在桥接仓库（跟人格、版本走） |
| `config.json` | 配置（含 `memory.dir`、`logDir`） | 能 | 留在桥接仓库（程序配置） |
| `scripts\backfill-memory-from-session.mjs`、`test-memory.mjs` | 工具/测试 | 随程序迁移 | 进新程序仓库 |
| `<BACKUP_ROOT>\dsmp-memory` | 备份 | 不动 | 备份源路径保持，备份程序适配新布局 |

**判断「是不是记忆」的标准**：能否重建。原文/摘要/事实卡丢了就回不来 → 算记忆；`sessions.json` 丢了最多重建会话 → 算状态。状态文件不进 shenming，避免把它也当成需要长期保存的东西。

## 2. 数据集中方案

### 2.1 DSH 原生记忆（唯一的硬骨头）

`~\.dsh\memories` 由 DSH 按 `DSH_HOME` 拼出来，没有配置项单独改目录（改 `DSH_HOME` 会连 `sessions\`、`credentials.yaml` 一起搬，风险大，不推荐）。两个选择：

1. **junction（推荐先试）**：把 `<USER_HOME>\.dsh\memories` 改名备份，然后
   `cmd /c mklink /J "<USER_HOME>\.dsh\memories" "<DSMP_MEMORY_DIR>\dsh-memories"`
   - 优点：物理上真在 D 盘，零同步。
   - 风险：DSH 写入时若用「临时文件 + rename」跨卷会失败；升级 DSH 后目录可能被重建。**先在副本上验证写入再切**。
2. **镜像（保守）**：保持 `~\.dsh\memories` 原样，加一个每日任务把整个目录 `robocopy /MIR` 到 `shenming\dsh-memories\`。
   - 优点：零侵入、可回滚；缺点：两份数据，读旧的要记得读镜像。

### 2.2 目标布局（数据根 `MEMORY_HOME = <DSMP_MEMORY_DIR>`）

```
shenming\
  raw\hot\YYYY-MM-DD\private_<OWNER_QQ>.jsonl
  raw\archive\YYYY-MM\private_<OWNER_QQ>-YYYY-MM-DD.jsonl
  digests\private_<OWNER_QQ>-<stamp>.md
  profile.md
  profile.md.bak-*
  state\memory.json          # 记忆自己的状态（不是桥接状态）
  dsh-memories\              # DSH 原生记忆（junction 或镜像）
  logs\                      # 运行日志（logDir）
  meta.json                  # schemaVersion、lastMigration、来源信息
```

兼容策略：读取时**先看新布局，再看旧布局**（`hot\`、`archive\` 仍在根下就继续读），迁移脚本负责搬 + 留 `.migrated-to-raw` 标记；写入一律走新布局。这样切换期间不会半新半旧读不到。

### 2.3 迁移步骤

1. 停桥接（`stop-bridge.cmd`）。
2. 备份整个 `shenming`（robocopy 到 `<BACKUP_ROOT>` 或同级 `.bak-20261027`）。
3. 跑 `scripts/migrate-memory-layout.mjs`（新程序里）：`hot\*` → `raw\hot\*`、`archive\*` → `raw\archive\*`，写 `meta.json`，旧目录留空壳 + 标记。
4. 起桥接，验证检索/日终/轮转路径日志。
5. 决定 DSH 原生记忆走 junction 还是镜像（§2.1）。

## 3. 程序独立方案

### 3.1 三种形态对比

| 形态 | 做法 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| **A 本地库 + 薄适配**（推荐） | 把 `src/memory-store.js`、`src/memory-digest.js` 变成独立包 `@local/deepseek-memory`；qq-bridge 只留 `bridge-memory.js` 适配层（采集/注入/轮转调度） | 改动小（接口基本不变）、单进程、调试简单、升级 = 换包 | 仍与桥接同进程；别的程序要用得自己 import | 现在就是单机单 Bot，先落地这个 |
| **B 独立 sidecar** | 新程序起 HTTP 服务（如 `127.0.0.1:3220`）：`/append` `/search` `/handover/peek|clear` `/maintenance` `/stats`；桥接/CLI/DSH 都通过 HTTP 调 | 真正解耦，多程序共用；可独立重启/升级；能加鉴权 | 多一个进程要守护；失败模式多（超时/重试）；延迟略增 | 以后要让 DSH 本体或别的 Bot 也读同一份记忆 |
| **C DSH Cordis 插件** | 在 DSH 里加页面/工具（记忆浏览、检索、事实卡编辑） | UI 好看，能在 DSH 里用 | 采集不到 QQ 消息（消息在桥接里），只能做查看/查询 | 作为 B 之上的面板 |

**推荐路径：A →（有第二个消费方时）B → C 做面板。** 不要一上来就 C，因为记忆的写入源头是 QQ 桥接，不在 DSH。

### 3.2 新程序仓库 `<DSMP_MEMORY_SRC>\`

```
package.json                 # name: "@local/deepseek-memory", type: module, engines.node >=22.13
src\store.mjs                # 原 memory-store.js（纯文件层，无外部依赖）
src\digest.mjs               # 原 memory-digest.js（模型摘要/事实卡，复用 webSearch key）
src\config.mjs               # 读 memory 段配置 + 默认值 + 校验
src\migrate.mjs              # 旧布局 → raw\ 迁移
src\mcp-server.mjs           # stdio MCP：qq_memory_search / qq_memory_day / qq_memory_profile
src\adapter-bridge.mjs       # 给 qq-bridge 的薄适配（导出 recordIncoming/recordOutgoing/noteSession/
                             #   composePromptWithMemory/ensureFallbackHandover/maybeRotate/dailyTick）
scripts\backfill-from-session.mjs
test\memory.test.mjs         # 原 test-memory.mjs（20 场景）
docs\README.md               # 数据布局、接口、迁移、回滚
```

接口约定（适配层）：桥接只 import 一个文件 `bridge-memory.js`，它内部再调包。这样以后从 A 换成 B，只改适配层，桥接业务代码（17 处调用点）不动。

### 3.3 qq-bridge 侧改动

1. `package.json` 加 `"@local/deepseek-memory": "file:../DeepSeek memory"`（或用 `scripts\link-memory.mjs` 建 junction 到 `node_modules\@local`，离线环境更稳）。
2. `src/bridge.js` 的 2 个 import 改成 `import … from './bridge-memory.js'`。
3. 记忆相关端点（`memory-search`、`memory-maintenance`）保留在桥接，内部转调包；MCP 工具 `qq_memory_search` 从 `mcp-snowluma-safe.js` 迁到新包的 `mcp-server.mjs`。
4. `cordis.patch.yml` 增加一个 MCP server 条目（名字建议 `deepseek-memory`），只让它注册 `qq_memory_*`；**同一次改完要刷新所有 server，避免同名工具重复注册**（DSH 重启后生效）。
5. 备份脚本的源路径改为：`shenming` 整棵树 + `~\.dsh\memories`（若走镜像）。

### 3.4 迁移步骤（建议一次 PR 完成）

1. 新建仓库，从桥接复制 4 个文件（store/digest/test/backfill），改 import 路径，跑通 20 场景测试。
2. 桥接加 `bridge-memory.js` 适配层，先**双注册**（旧文件仍保留）但只走新包；用 config `memory.impl: "package"` 切换，出问题改回 `"legacy"`。
3. 数据布局迁移（§2.3）。
4. MCP 工具迁移 + DSH 重启验证。
5. 桥接全链路回归：日志写入、检索、日终、强制轮转、注入一次、新会话兜底、重启持久化。
6. 删除桥接里的旧复制文件，更新 README/HANDOFF/备份文档。

## 4. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 中文 + 空格路径在脚本/依赖里踩坑 | 仓库目录建议改英文 `deepseek-memory`；若必须用中文，所有脚本加引号并在测试里覆盖 |
| junction `~\.dsh\memories` 写入出现 EXDEV/rename 失败 | 先副本验证；失败改用镜像方案，不动 DSH |
| 桥接与 CLI/sidecar 同时写同一 hot 文件 | A 形态单进程不存在；B 形态加文件锁（`proper-lockfile` 或 O_EXCL 锁文件），或全部写请求走 sidecar |
| MCP 工具重名 | 迁工具时从 `mcp-snowluma-safe.js` 删除旧定义，只在新 server 注册；DSH 重启后 `tools/list` 验证 count |
| 迁移中途半新半旧 | 读取兼容旧布局；迁移脚本幂等；写 `meta.json` 标记 |
| 备份脚本路径失效 | 迁移同 PR 更新备份脚本 + 跑一次热备验证 SHA256 |
| 事实卡/摘要模型 key 解析依赖 qq-bridge 的 `web-search.js` | 把 key 解析（config.webSearch → DEEPSEEK_API_KEY → DSH 凭据）抽进新包的 `config.mjs`，不依赖桥接内部模块 |

## 7. 明确不做（本方案外）

- 不搬 `state\sessions.json` / `social-v2.json` 等桥接状态文件（会破坏映射）。
- 不改 `DSH_HOME` 环境变量。
- 不引入向量库/embedding（检索仍按关键词+日期；需要语义检索另起方案）。
- 不动 `roles\<PERSONA>.md` 到数据目录（角色卡跟程序走）。
